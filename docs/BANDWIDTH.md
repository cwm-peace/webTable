# 打包体积与 10 Mbps 带宽

2026-10-17 本机生产构建测量。这里把“10M 带宽”按服务器出口 **10 Mbps** 计算，理论字节速率为 1.25 MB/s；若购买的是 10 MB/s，应换算成 80 Mbps。MB/GB 为十进制；图片限制的 MiB 为二进制。

## 修复后的实际资源预算

| 场景 | 优化前 gzip | 当前 gzip | 优化前 Brotli | 当前 Brotli |
| --- | ---: | ---: | ---: | ---: |
| 首次打开首页 | 0.106 MB | 0.106 MB | 0.107 MB | 0.091 MB |
| 首次处理图片额外加载 | 0.002 MB | 0.002 MB | 0.002 MB | 0.002 MB |
| 首次导出额外加载 PDF 模块与字库 | 7.721 MB | 6.392 MB | 7.950 MB | 5.230 MB |
| 一次完整冷缓存使用 | 7.829 MB | 6.500 MB | 8.059 MB | 5.323 MB |

gzip 完整使用流量减少约17%，Brotli减少约34%。优化前是原字库与请求时gzip级别6/Brotli质量4；当前是优化字库与构建时gzip级别9/Brotli质量11，表中是组合效果。**标准 Nginx 按 gzip 列预算**，安装并启用 Brotli 模块才会得到 Brotli 列效果。

字库仍是主要资源：原文件8,331,336字节，当前6,935,324字节；gzip为5,876,648字节，Brotli为4,804,883字节。保留全部30,890码位及排版特性，逐码位检查轮廓和水平度量一致，仅移除hinting与不可达字形。浏览器中继续完整嵌入字库，避免之前的CFF运行时子集显示问题。

未压缩资源约9.60 MB；包含gzip和Brotli旁文件的发布目录约22.34 MB。旁文件是同一资源的替代传输表示，浏览器按协商只下载一种，不能把三份文件相加当作用户流量。

Chromium首页冷缓存实际传输约92 KB，立即刷新约822字节，脚本和样式复用缓存。PDF和字体仍按需加载。字库使用内容哈希URL，和构建资源一样缓存一年；普通重复访问可复用，强制刷新或浏览器清缓存后仍可能重新传输。HTML保持重新验证。

机器证据见 [bandwidth-20261017.json](verification/bandwidth-20261017.json)。优化前对照保存在本机忽略目录 `artifacts/bandwidth-before-jpeg-font-20261017.json`；原 [bandwidth.json](verification/bandwidth.json) 保留历史及既有未提交数据，不覆盖。

## 10 Mbps 能承担什么

以下为所有人同时冷缓存导出、平均共享10 Mbps出口时，**仅静态下载的理论耗时**，不包含连接、TLS、网络重传、字体解析、图片处理与PDF生成时间。

| 同时首次导出人数 | gzip 下载时间 | Brotli 下载时间 |
| --- | ---: | ---: |
| 1 | 5.1 秒 | 4.2 秒 |
| 5 | 25.6 秒 | 20.9 秒 |
| 10 | 51.1 秒 | 41.8 秒 |
| 20 | 102.3 秒 | 83.7 秒 |

实际应留出至少约30%的规划余量，而不是把理论值作为完成时间保证。100人在线不代表100人同时下载字库。普通首页仅约0.1 MB，小规模打开与填写主要受本机处理能力影响；集中首次导出才是10 Mbps出口的瓶颈。每月1万次完整冷缓存使用约65 GB（gzip）或53 GB（Brotli）正文，另计协议和重传。

计算式：`秒数 = 单人传输MB × 8 × 同时人数 ÷ 带宽Mbps`。本机回环测量给出的是传输字节数与缓存证据，不是公网延迟或容量保证。

## 字体与部署

- 网页已使用访问者的系统字体；Linux服务器上的系统字体或新装字体不会自动提供给访问者。当前应用没有服务器PDF生成，也无需服务器字体包。
- PDF生成器需要可读取、可嵌入的字体字节，不能把CSS的系统字体名称直接当成字体文件。当前采用同源字库；不引入远程字体、第三方CDN或填写数据外发。
- `npm run build`自动生成`.gz`/`.br`，一起发布完整`dist/`；构建机承担高等级压缩，静态服务器优先直接读取旁文件。旁文件过期或为符号链接时，本机预览服务回退即时压缩。
- `deploy/nginx.conf`设置OTF的正确Content-Type，确保字体命中gzip类型列表；内容版本字体使用一年immutable缓存。Nginx配置需在目标主机执行`nginx -t`及响应头核验；本次既有Linux站点结果见下文。

复测：`npm run build`后执行`node scripts/measure-bandwidth.mjs --output artifacts/bandwidth-current.json`。脚本按实际预压缩文件计算，排除`.gz`/`.br`重复下载计数，并验证HTTP编码、ETag、304及首页缓存。

## 同日既有服务器实测

实际 Linux 站点此前把 OTF 作为 `application/octet-stream` 返回，未命中 `gzip_types`，旧字库实际下载8,331,336字节。新发布补齐类型映射并启用动态gzip后，实际响应为 `font/otf` + `Content-Encoding: gzip`，5,879,355字节，**相对该站点原字体传输减少29.43%**。这与上表“已有gzip情况下”的本机前后对照不是同一个基线。

现场Nginx未编译gzip_static或Brotli，所以暂不享有预压缩旁文件和Brotli的服务器CPU／流量收益；没有为此替换服务二进制。字库一年缓存、条件请求304、新旧版本资源与`/bdsm/`路径均已验证。公网单次下载观测约8.4秒，只是本次链路观测，不代表10 Mbps满速或延迟保证。证据见 `verification/deployment-20261017.json`。

后续同日加固已切换至支持gzip_static的官方Nginx1.30.6；此后线上字体直接发送5,876,648字节的构建gzip旁文件。回环各6次顺序下载对照，中位耗时旧0.762秒、新0.284秒，期间worker累计CPU旧4.22秒、新1.51秒；短样本不作为公网时延或固定提升比例保证。改动主要减少服务端重复压缩，10 Mbps出口限额不变，Brotli仍未启用。
