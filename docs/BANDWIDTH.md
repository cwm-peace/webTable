# 打包体积与带宽

2026-10-14生产构建实测。单位MB/GB按十进制计，图片容量限制中的MiB按二进制计。原始发布目录约10.97 MB，包含中文字体、PDF Worker和主线程回退模块；服务器只需保存这一份静态包，不保存用户图片或PDF。

| 使用场景 | gzip正文流量 | Brotli质量4正文流量 |
| --- | ---: | ---: |
| 首次打开首页 | 0.104 MB | 0.105 MB |
| 第一次处理图片额外加载 | 0.002 MB | 0.002 MB |
| 首次导出额外加载PDF模块和中文字体 | 7.72 MB | 7.95 MB |
| 一次完整冷缓存使用 | 7.82 MB | 8.05 MB |
| 所有发布文件逐一加载（含通常不用的回退模块、许可） | 8.33 MB | 8.56 MB |

实际Chromium首页冷缓存传输约0.106 MB，立即刷新约822字节，脚本与样式命中浏览器缓存。逐文件真实HTTP协商与ETag 304检查通过，详见`verification/bandwidth.json`。正文预算不含HTTP/TLS开销、网络重传及托管商计费差异。完整使用流量由实际构建依赖和HTTP压缩表示相加；不是声称每个浏览器每次都会下载全部模块。

主要流量来自8.33 MB原始中文字体。它只在首次导出时加载，压缩后仍约7.2–7.4 MB。完整嵌入用于保留填写内容的中文显示；经过测试的CFF字体子集存在显示问题，因此当前版本采用完整字体。再次导出可复用缓存；本地图片与PDF不上传，所以16张图片再大，也不会增加服务器的图片传输量。

## 容量建议

- 每月1万次完整冷缓存使用，静态正文约78–81 GB；计入余量建议准备100–120 GB/月。
- 每月10万次完整冷缓存使用，正文约0.78–0.81 TB；建议约1 TB/月。实际缓存命中可降低用量。
- 100人同时首次打开首页，希望10秒内完成，仅首页约需11 Mbps（含30%余量）。20 Mbps以上可作小规模静态部署起点。
- 100人同时首次导出，希望10秒内完成字体和模块加载，约需0.81–0.84 Gbps（含30%余量）。这一峰值可用静态CDN缓存或更高入口带宽承担；20 Mbps单机不能保证这个目标。

计算式：`带宽Mbps = 每人传输MB × 8 × 同时人数 ÷ 目标秒数 × 余量系数`。100人在线不等于100人同时下载字体；须按实际访问峰值选择资源。

建议先用支持HTTPS、gzip、缓存控制的静态托管或20–50 Mbps入口，按导出峰值决定是否加CDN。CDN是可选部署方案，当前代码没有外部CDN请求；采用时须另外核对访问日志、IP处理与缓存政策。不要把本机静态压测的吞吐当作公网线路保证。

复测：`npm run build`后执行`node scripts/measure-bandwidth.mjs`。若更换字体、依赖或压缩配置，应重新测量。此前18–22 MB构建预算已被以上实测取代。
